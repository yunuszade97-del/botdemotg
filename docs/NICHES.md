# Ниши: один бот — разные бизнесы

Бот не привязан к автопрокату. Ниша — это данные, а не код: прайс, набор
уточняющих вопросов и приветствие. Меняются одной переменной в `.env`.

```bash
PROFILE=tours     # и перезапуск
```

---

## Готовые ниши

```bash
.venv/bin/python -m app.profiles
```

| `PROFILE`     | Бизнес                          | Чем отличается диалог                          |
|---------------|---------------------------------|------------------------------------------------|
| `rent_car`    | аренда автомобилей              | спрашивает стаж и возраст — без них аренда невозможна |
| `real_estate` | аренда квартир и апартаментов   | район, количество спален, животные, бюджет в месяц |
| `tours`       | экскурсии и трансферы           | сколько человек, возраст детей, откуда забирать |

Посмотреть карточку ниши и сценарий для демо:

```bash
.venv/bin/python -m app.profiles show tours
```

Посмотреть системный промпт целиком — ровно то, что увидит модель:

```bash
.venv/bin/python -m app.profiles prompt tours
```

## Как устроен профиль

Два файла на нишу:

```
profiles/tours.toml          ← кто вы и что спрашивать (правит разработчик)
content/niches/tours.md      ← прайс, условия, FAQ (правит менеджер клиента)
```

Разделены намеренно: прайс меняется каждую неделю и его правит человек,
далёкий от кода. Ошибка в markdown не может уронить запуск — а ошибка
в TOML уронит, поэтому в TOML лежит только то, что меняется редко.

`profiles/tours.toml`:

```toml
name = "Georgia Travel"                         # как бот представляется
business = "экскурсии и трансферы по Грузии"
city = "Батуми"
working_hours = "ежедневно 08:00–22:00"
response_time = "5 минут"                       # что обещаем клиенту
knowledge_file = "content/niches/tours.md"

welcome = """..."""                             # первое сообщение на /start

qualify = [                                     # ← главное отличие ниш
  "направление: конкретная экскурсия или трансфер откуда-куда",
  "сколько человек, есть ли дети и их возраст",
]

demo_script = ["Здравствуйте! Хотим съездить в Кутаиси", "..."]
```

`qualify` вклеивается прямо в системный промпт отдельным блоком. Именно
из-за него прокату бот спросит стаж вождения, а экскурсиям — возраст детей.
Без него получаются заявки, с которыми менеджер не может работать без
второго звонка — а второй звонок это половина потерянных лидов.

`demo_script` нигде не влияет на работу бота: это сценарий для ручного
прогона перед встречей с клиентом.

## Один шаблон — много клиентов

Профиль задаёт нишу, `.env` — конкретного клиента. Любая переменная
`COMPANY_*` перебивает профиль:

```bash
PROFILE=tours
COMPANY_NAME=Ольга Travel
COMPANY_CITY=Тбилиси
```

Получится тот же экскурсионный бот с той же логикой квалификации, но под
другим именем и городом. Пустая строка (`COMPANY_CITY=`) перекрытием
**не** считается — значение возьмётся из профиля.

Так один профиль обслуживает десяток клиентов в одной нише: отличаются
только название, город и файл с прайсом.

## Своя ниша за 10 минут

Пример — барбершоп.

**1. Прайс и FAQ** → `content/niches/barbershop.md`

Структура важнее объёма. Берите за образец любой файл из `content/niches/`:
о компании → услуги и цены таблицей → условия → частые вопросы → стоп-темы.

Раздел **«Стоп-темы»** не пропускайте: там перечислено, что бот НЕ подтверждает
сам (точное наличие, индивидуальные скидки, гарантии). Без него модель начнёт
обещать то, чего вы не выполните.

**2. Профиль** → `profiles/barbershop.toml`

```toml
name = "Sharp"
business = "мужские стрижки и барбершоп"
city = "Батуми"
working_hours = "ежедневно 10:00–21:00"
response_time = "10 минут"
knowledge_file = "content/niches/barbershop.md"

welcome = """
Здравствуйте! 👋 Это Sharp — барбершоп в центре Батуми.

Скажите, к какому мастеру и на какое время удобно — подберу окно в записи."""

qualify = [
  "услуга: стрижка, борода, комплекс",
  "желаемая дата и время",
  "конкретный мастер или любой свободный",
]

demo_script = [
  "Здравствуйте, сколько стоит стрижка с бородой?",
  "давайте в субботу вечером",
  "Дмитрий, +995 555 00 11 22",
]
```

**3. Включите и проверьте**

```bash
sed -i 's/^PROFILE=.*/PROFILE=barbershop/' .env
.venv/bin/python -m app.profiles show barbershop
.venv/bin/python -m app.profiles prompt barbershop   # прочитайте глазами
.venv/bin/python -m app.preflight
```

**4. Прогоните `demo_script` живьём.** Промпт, который хорошо читается,
и промпт, который доводит до заявки, — разные вещи. Проверяется только диалогом.

## Что подсказывает опыт

**`qualify` — это 3–5 пунктов, а не анкета.** Бот задаёт по одному вопросу
за ход. Десять пунктов превращают диалог в допрос, и клиент уходит.
Оставляйте только то, без чего менеджер физически не сможет работать.

**Пишите `qualify` как причину, а не как поле.** Сравните: «возраст» против
«возраст водителя и стаж — от 21 года и 2 лет, иначе аренда невозможна».
Второе модель использует осмысленно: сама объяснит клиенту, зачем спрашивает.

**Проверяйте, что бот не выдумывает.** Спросите то, чего в базе знаний нет.
Правильный ответ — «уточню у менеджера», а не придуманная цифра. Если
выдумывает, значит в базе знаний слишком мало конкретики.

**Цены держите в базе знаний, тон — в промпте.** `app/core/prompts.py` — это
про стиль и логику продаж, он общий для всех ниш. Факты о бизнесе туда
не переносите, иначе смена клиента снова станет правкой кода.

## Если ниша не влезает в шаблон

Профиль закрывает случай «услуга → квалификация → заявка». Он не подойдёт,
если нужны:

- **подбор из каталога с фото** — модели нужен доступ к базе объектов, а не
  текстовый прайс;
- **проверка занятости в реальном времени** — это отдельный инструмент
  рядом с `save_qualified_lead` (см. `app/core/tools.py`);
- **онлайн-оплата** — отдельный сценарий, MVP до неё не доходит.

Всё это добавляется инструментами, не форком: см. «Инварианты» в
[CLAUDE.md](../CLAUDE.md) — там записано, что легко сломать по дороге.
