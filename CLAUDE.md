# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Telegram-бот для лидогенерации в услугах/аренде: LLM ведёт диалог как менеджер
по продажам и через function calling сохраняет квалифицированную заявку.
Стек: Python 3.11+, aiogram 3, FastAPI, OpenAI-совместимый LLM API, SQLite.

Комментарии, докстринги и сообщения пользователю — на русском. В коммитах
заголовок на английском, тело на русском; тело объясняет, какой отказ закрывает
изменение, а не пересказывает диff.

Начиная работу, прочитайте [docs/ROADMAP.md](docs/ROADMAP.md): что уже сделано и
почему, что осталось, где известные слабые места и в каком состоянии ветка.

## Команды

```bash
python3.11 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt

.venv/bin/python -m pytest -q                              # весь набор (~4 с)
.venv/bin/python -m pytest tests/test_conversation.py -q    # один файл
.venv/bin/python -m pytest -q -k "duplicate or throttl"     # по имени
.venv/bin/python -m pytest tests/test_aggregator.py::test_chats_do_not_mix -q

.venv/bin/python -m app.preflight   # проверка готовности; код возврата 1 = не запускать
.venv/bin/python -m app.main        # запуск (polling или webhook по USE_WEBHOOK)

.venv/bin/python -m app.profiles              # список ниш
.venv/bin/python -m app.profiles show tours   # карточка ниши и сценарий демо
.venv/bin/python -m app.profiles prompt tours # системный промпт целиком
```

Линтера и форматтера в проекте нет — стиль поддерживается вручную по
окружающему коду. CI (`.github/workflows/ci.yml`) гоняет `pytest` на 3.11, 3.12
и 3.13 плюс сборку приложения с минимальным конфигом.

Версии зависимостей закреплены точно (`==`), не диапазонами: хостинг-панель
делает `pip install -U` на каждом запуске, и с диапазонами рестарт привозил бы
новый мажор без единой правки в коде. Обновление версии — отдельный коммит
с прогоном тестов; ослаблять закрепление обратно нельзя.

## Архитектура

Поток одного сообщения:

```
Telegram → FastAPI (webhook) | polling
        → Dispatcher → LoggingMiddleware → ChatGuardMiddleware → ThrottlingMiddleware
        → handlers/dialog.py → MessageAggregator (пауза) → ConversationService
        → LLM + tools ─┬→ save_qualified_lead → БД → AdminNotifier + LeadWebhookSender
                       └→ request_phone_button → кнопка контакта
```

`app/main.py` — единственная точка входа для обоих режимов. FastAPI поднимается
всегда (нужен `/healthz`), polling живёт фоновой задачей внутри `lifespan`.
Там же собираются все сервисы и запускается цикл очистки данных.

`ConversationService` (`app/bot/services/conversation.py`) — центр системы;
почти вся нетривиальная логика здесь, изменения чаще всего затрагивают именно
его. Он владеет tool-loop, дедупом лидов, лимитами и фоновыми задачами.

Слои разделены так, что `ConversationService` не знает про aiogram, а хэндлеры
не знают про LLM. Тесты этим пользуются: сервис тестируется без Telegram,
хэндлеры — без сети.

## Инварианты, которые легко сломать

Каждый из них закрывает конкретный отказ и покрыт тестом. Меняя их, сначала
прочитайте тест — там записано, что именно ломалось.

**Tool calling — это два прохода к модели.** После `save_qualified_lead`
результат возвращается модели tool-сообщением, и она генерирует подтверждение.
Один проход оставляет клиента без ответа.

**Раунды с `tool_calls` не пишутся в историю.** В БД идут только текстовые ходы.
Сохранённое `assistant`-сообщение с `tool_calls` без парного `tool`-ответа
роняет следующий запрос к API в 400 — и бот начинает отвечать ошибкой каждому,
кто когда-либо оставил заявку.

**Аргументы инструмента — недоверенный ввод.** Их пишет модель. Валидация
в `app/core/schemas.py`; при отказе модель получает ошибку и переспрашивает
клиента, а лид не создаётся.

**`normalize_contact()` возвращает ключ дедупа, а не «красивый» номер.**
Телефон сводится к последним 10 цифрам (`tel:9991234567`). Менеджеру уходит
`phone_or_contact` в исходном виде.

**Бот никогда не молчит.** Сбой LLM, исчерпанный лимит, упавший хэндлер —
везде есть ответ клиенту. Молчание бота равно потерянному лиду.

**Лид сохраняется в БД до любой доставки.** Уведомление админу и внешний вебхук
идут фоном и независимо; провал оставляет `admin_notified` / `webhook_delivered`
в 0, и запись досылается при следующем старте.

**Подряд идущие сообщения склеиваются, а не отбрасываются.** Люди пишут имя,
телефон и даты тремя сообщениями. `MessageAggregator` копит их и отдаёт модели
одним ходом; поэтому `THROTTLE_MIN_INTERVAL` по умолчанию 0.

**Фоновые задачи требуют сильной ссылки.** asyncio хранит задачи только слабо.
Используйте `ConversationService._spawn()` или добавляйте задачу в набор
вручную — иначе сборщик мусора отменит отправку лида на середине.

**Провал старта обязан освободить ресурсы, а не просто выбросить исключение.**
Всё, что открывает `lifespan`, регистрируется в `AsyncExitStack`. aiosqlite
обслуживает соединение НЕ-демоническим потоком: незакрытая база держит
интерпретатор после «Application startup failed. Exiting.» — процесс остаётся
жив навсегда, порт не слушает, а systemd, Docker и панель видят живой процесс
и перезапуск не запускают. Бот лежит молча.

**Polling запускается с `handle_signals=False`.** `loop.add_signal_handler`
не добавляет обработчик, а заменяет поставленный uvicorn. С умолчанием aiogram
SIGTERM останавливает только polling: uvicorn не узнаёт, что пора выключаться,
и процесс продолжает работать с оглохшим ботом до тех пор, пока супервизор
не добьёт его по таймауту.

**`/healthz` отвечает `ok` только при живом polling.** Живой процесс не равен
работающему боту. Пока healthcheck зелёный при мёртвом polling, отказ не видят
ни панель, ни внешний мониторинг — и «бот молчит» выясняется от клиентов.

**Кулдауны сравниваются через сентинел `None`, а не `dict.get(key, 0.0)`.**
`time.monotonic()` отсчитывается от произвольной точки: с нулём по умолчанию
на свежезапущенной машине подавляются первый алерт и первое сообщение каждого
клиента — то есть сразу после каждого деплоя.

**Роутеры собираются фабриками `build_router()`.** Модульный синглтон нельзя
включить во второй `Dispatcher` — aiogram бросает «Router is already attached».

**Новая колонка в БД требует записи в `MIGRATIONS`** (`app/db/models.py`).
`CREATE TABLE IF NOT EXISTS` не меняет существующую таблицу, и обновление кода
на работающем боте упадёт на первом же запросе.

**Секрет вебхука проверяется до обращения к `app.state`.** Проверка не должна
зависеть от того, отработал ли `lifespan`.

**Неизвестный `PROFILE` роняет старт, а не откатывается к умолчаниям.** Бот,
молча уехавший на чужой прайс, выглядит полностью рабочим и продаёт не то.

**Пустая строка в `.env` не перекрывает профиль.** Для pydantic
`WELCOME_MESSAGE=` — заданное значение; считать его перекрытием значит молча
стереть приветствие профиля строкой, которую никто не писал осознанно.

**Тесты не читают `.env`** (`_ignore_dotenv`, autouse в `tests/conftest.py`).
Settings берёт из него любое поле, не переданное явно, — набор начинает
вести себя по-разному локально и в CI, и зелёные тесты перестают что-либо
доказывать.

**При выключенной витрине поведение не меняется буквально.** Промпт,
карточка лида, payload вебхука, `allowed_updates`, вывод preflight — всё
это уже развёрнуто у клиентов на обычном `PROFILE`. Правка в коде витрины,
которая задевает эти пути без проверки `SHOWCASE_PROFILES`, тихо меняет
поведение бота, за которым никто не следит, потому что никто не ждал изменений.

**До выбора ниши — ни вызова LLM, ни записи в историю, ни инкремента
суточного счётчика.** Ниша не выбрана — отвечать клиенту нечем, а платить
за случайную нишу или тратить дневной лимит на выбор направления не за что.

**`switch_niche` сначала чистит историю, потом пишет `profile_slug`.**
Обратный порядок при сбое между операциями оставляет новый промпт со старой
историей — модель продолжит разговор в новой нише репликами клиента из
прежней.

**Очередь агрегатора сбрасывается до переключения ниши, не после.**
`MessageAggregator.cancel()` вызывается раньше `switch_niche`: иначе таймер
флаша, ждущий тот же лок чата, получает его уже после переключения и уносит
в модель текст из прежней ниши с промптом и базой знаний уже новой.

**Middleware на `callback_query` навешаны через `outer_middleware`, а не
через обычный `.middleware()`.** Обычная (inner) middleware у aiogram не
вызывается, пока для события не найден хэндлер, а хэндлер на `callback_query`
есть только при включённой витрине — на обычном боте ChatGuard и троттлинг
были бы мёртвым кодом для нажатий кнопок.

**Роутер ниш подключается только при включённой витрине.** Он появляется в
дереве роутеров условием в `handlers.build_router(showcase_enabled=...)`.
Подключить его безусловно — значит завести в дереве callback_query-хэндлер
у клиента без витрины, а `allowed_updates` в `setWebhook` считается по факту
наличия хэндлеров: у проданного бота молча изменится набор апдейтов,
которые Telegram вообще присылает.

## Ниши и настройка под клиента

`PROFILE=<имя>` в `.env` разворачивается в бизнес-блок `Settings` из
`profiles/<имя>.toml` (`app/core/profile.py`, вызов в `Settings.model_post_init`).
Профиль несёт название, направление, город, часы работы, приветствие, путь
к базе знаний и `qualify` — список того, что выяснить именно в этой нише;
`qualify` вклеивается в системный промпт отдельным блоком.

Прайс и FAQ лежат отдельным markdown (`content/niches/<имя>.md`): его правит
менеджер клиента, и ошибка там не должна ронять загрузку конфига.

Любая переменная `COMPANY_*` в `.env` перебивает профиль точечно — один
шаблон ниши обслуживает разных клиентов. Подробности — `docs/NICHES.md`,
запуск демо — `docs/LAUNCH.md`.

Тон и логика продаж живут в `app/core/prompts.py` и общие для всех ниш —
это про стиль, не про факты о бизнесе.

**Режим витрины** (`SHOWCASE_PROFILES=rent_car,real_estate,tours` в `.env`)
делает нишу свойством чата, а не только процесса. `app/core/niches.py`
(`NicheRegistry`) на старте компилирует системный промпт для каждого
перечисленного профиля — чтение базы знаний и сборка промпта не должны
блокировать event loop на каждом сообщении. Выбор клиента хранится в
`users.profile_slug` (`Repository.get_chat_profile` / `set_chat_profile`);
пока эта колонка пуста для чата, диалог для него не начинается — ни один
запрос к модели не уходит без выбранной ниши. Реестр пуст, когда
`SHOWCASE_PROFILES` не задан, — это и есть обычный однонишевый режим.

Смена LLM-провайдера — две переменные (`LLM_BASE_URL`, `LLM_MODEL`); работает
любой OpenAI-совместимый API с поддержкой tool calling.

## Тесты

`asyncio_mode = auto` — async-тесты не нужно помечать декоратором.

Полезное из `tests/conftest.py`: фикстура `make_service` собирает
`ConversationService` с `FakeLLM` (очередь заранее заданных ответов) и
`FakeNotifier`; `text_response()` и `tool_response()` конструируют ответы модели.
`tests/test_integration.py` даёт `MockedSession` (перехват вызовов Bot API),
`_make_dispatcher()` и `_update()` для сквозных проверок через диспетчер.

Тестовая фикстура `settings` выключает склейку сообщений
(`message_aggregation_delay=0.0`) ради детерминизма; сама склейка проверяется
в `tests/test_aggregator.py` с малой задержкой. Задержки ретраев в тестах
обнуляются (`retry_base_delay=0.0`) — набор должен оставаться быстрым.

Дублёры в `conftest.py` обязаны повторять интерфейс настоящих сервисов: при
добавлении метода в `AdminNotifier` его нужно добавить и в `FakeNotifier`.
